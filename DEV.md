# Developer runbook

## Layout

| Path | What it does |
|---|---|
| `app.py` | FastAPI routes, sign-in, upload handling, background job wiring |
| `config.py` | Paths, limits, model settings (read from the environment when called) |
| `store.py` | SQLite schema and every query (analyses, units, ratings, metrics, jobs, Vibe Check runs and history) |
| `model.py` | Ollama over HTTP (`local_model_call`, `local_model_ready`) |
| `analysis.py` | The 13-signal rating, FAS metrics and guidance (the original FELIXA engine) |
| `pipeline.py` | The worker: full run (behaviour analysis, then Vibe Check) and Vibe Check on its own |
| `report.py`, `bei_charts.py`, `report_export.py` | Report context, attribute charts, PDF and CSV |
| `vibe_check/` | The Vibe Check package (engine, ingest, forecast, charts, render, CLI) |
| `templates/`, `static/` | Pages and styles. `_results.html` is shared by the workspace and the report |
| `tests/` | `test_vibe_check.py` (engine), `test_app.py` (web app, the hosted launcher `start_online.py` with its processes faked, and `run_mac.command` run against a stand-in `ollama`), `fake_ollama.py` (stand-in model) |

## Set up

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
```

Run the `pip install` again whenever `requirements.txt` changes. An environment built before a pin was raised keeps the old release, and the pin test only reads the file. `test_a_pdf_stream_that_unpacks_to_hundreds_of_megabytes_is_stopped` runs the installed pypdf, which reads every uploaded PDF, and fails on an old one.

## Keep the pins current

`requirements.txt` pins exact releases, so a fix in a dependency reaches the app only when its pin moves. Once the repository is on GitHub, `.github/dependabot.yml` asks for a weekly pull request per outdated pin. At any time, `.venv/bin/pip install pip-audit && .venv/bin/pip-audit -r requirements.txt` lists the pins that have a published vulnerability. After moving a pin, run the tests on the pinned versions and on the latest ones.

## Run the tests

```bash
.venv/bin/python -I -W ignore -m unittest discover -s tests
```

The web tests need `requirements-dev.txt`; without it (no `httpx`) they are skipped and only the engine tests run.

The web tests set `FELIXA_ALLOWED_HOSTS=testserver` (the Host that FastAPI's TestClient sends): without a password the app answers only to localhost names.

## Run the app without a model

The fake model answers in Ollama's shape using keyword rules. Its numbers mean nothing; it exists to exercise the whole app.

```bash
.venv/bin/python tests/fake_ollama.py --port 11500 --model qwen2.5:7b
```

```bash
FELIXA_DATA_DIR=/tmp/bei-data FELIXA_OLLAMA_URL=http://127.0.0.1:11500 FELIXA_LOCAL_MODEL=qwen2.5:7b .venv/bin/python -m uvicorn app:app --port 5055
```

Open http://127.0.0.1:5055. Sample files are in `sample_data/`.

## Run against a real model

```bash
ollama pull qwen2.5:7b && .venv/bin/python app.py
```

## Rules when several people or agents work at once

- Give each instance its own `FELIXA_DATA_DIR`, app port and fake-model port. Never share a data directory (starting the app deletes the leftover upload copies in its `uploads` folder, which would break a file another instance is reading).
- `FELIXA_OLLAMA_URL` points the app at a model server; the app never needs the default port 11434 in tests.
- Parsing, charts and reports are plain functions: prefer a unit test with a Python fake over a browser when you can.

## Conventions

- The model is always passed in as `call(instructions, input_text, schema=None) -> (text, model_name)`. It raises `ModelUnavailable` (`vibe_check/engine.py`) when the model cannot be reached or does not answer in time, and only then: the Vibe Check engine retries such a batch but does not split it. Any other exception reads as a bad answer (cut short, malformed, invalid), which a smaller batch can cure. Three batches in a row that cannot be analysed stop the run.
- Text that came from a user is escaped by Jinja or by `html.escape`. Generated HTML (`vibe_html`, `chart_html`) is the only thing marked `|safe`.
- A model answer is never trusted: it is parsed, validated, and rejected rather than defaulted. The one exception is the written text of a Vibe Check answer: wording that suggests bans, warnings or punishments is replaced with standard text (`_PUNITIVE` in `vibe_check/engine.py`), because a wording slip must not cost the numbers a retry would throw away.
- Starlette refuses one form field over 1 MB with a bare JSON 400 (a multipart field on every version; a browser's urlencoded post since 1.4). FastAPI reads `Form(...)` parameters with that default, before any dependency runs, so a field that can be large is read by hand with an explicit `max_part_size` in a dependency, and an over-limit post is answered with a note (see `read_paste` in `app.py`). `requirements.txt` pins Starlette 0.x, which does not limit an urlencoded field: also run the tests with the latest versions (`pip install -U fastapi`) when you touch form handling.
- A request body is limited before anything reads it, by `BodyLimit` in `app.py`: Starlette parses a form, and spools its files to disk, before any route or dependency runs, so a size check in a route comes too late (the 15 MB check in `ingest_files` runs after the whole upload has been received). `BodyLimit` is a pure ASGI middleware added before the sign-in one, which makes it the innermost, and it has to stay there: the sign-in middleware answers a visitor without reading the body and passes `/login` through to it, and a `BaseHTTPMiddleware` wraps an error raised from the `receive()` beneath it in an `ExceptionGroup`, which the pinned Starlette's form parser does not recognise, so a `BodyLimit` outside it would leave the files the parser has spooled open until the next garbage collection (a test covers it). `body_limit` chooses the limit by path from `MAX_UPLOAD_BYTES`, `MAX_UPLOAD_FILES` and `MAX_FORM_BYTES` in `config.py`: a route that takes files or a paste has to match `UPLOAD_PATH` or `PASTE_PATH`, or it is held to the small form limit (a test checks the route table). A declared length over the limit is refused unread. A body with none is counted as it is read, and the error that cuts it is a `MultiPartException` for the same reason. Starlette or FastAPI turns it into a 400 on most routes and the paste route's dependency lets it out on the pinned Starlette, so the middleware goes by its own flag, not by the error, and drops whatever the app answers after the cut. The upload forms also check the sizes in the browser (`templates/_file_check.html`), so that a file the server would refuse is not sent first; the limits reach the templates through the globals set in `app.py`.
- Every database connection comes from `store.db()`, the only caller of `sqlite3.connect`. It turns on `secure_delete`, so that SQLite overwrites what a statement deletes: a build that is not compiled with it on (Ubuntu's is) only marks the space free, and the text of a deleted message stays in `felixa.db`. While another connection has the file open, the write-ahead log also keeps the pages as they were before the delete, so code that deletes user data ends with `store.empty_log()`. `init_db` makes the database file owner-only (the `-wal` and `-shm` files take its mode), and `config.data_dir()` makes a folder it creates owner-only. A row in `vibe_history` outlives the evidence, so it holds numbers and a fingerprint of each source (`vibe_check.forecast.source_key`), never a message or a name. `stock_sqlite()` in `tests/test_app.py` runs a test on SQLite with `secure_delete` off, whichever build runs it.
- Every check of a username and password goes through `SignIn.attempt` in `app.py`, for the sign-in form and for HTTP Basic alike (a second check elsewhere would be a second door with its own, or no, limit). It keeps one count of wrong passwords per client address and raises `Throttled` (a 429 with `Retry-After`) while a client has to wait. Do not slow guessing with `time.sleep`: it runs in the thread pool, and a few hundred bad sign-ins at once then keep every thread busy and the rest of the app waits. A session is a random token that `SignIn` holds in memory (hashed), not something computed from the password, so `end_session` can revoke it and a captured cookie reveals nothing about the password; a restart signs everyone out, as the job queue already needs the app to be one process. The counts live in the process, so `AppCase.setUp` gives every web test a fresh `app.sign_in`, and a test moves time with `SignIn(clock=...)` instead of waiting. The session cookie is `Secure` and `__Host-` prefixed, so a browser keeps it only over https or at a localhost address: at a LAN IP or a host name over plain http the right password ends on the form again, silently. `login_page` therefore carries a notice (`#plain-http`) that a script shows when `window.isSecureContext` is false, the browser's own test for exactly that (the server cannot tell: behind a proxy that ends https it sees http), and `python app.py` warns at start-up when a password is set and `FELIXA_HOST` is beyond this computer. Do not add a non-Secure cookie option to make a LAN address work: it would send the password and the session token in the clear. A browser check needs a name other than localhost for the same server, for example `http://192.168.x.x:PORT` or Chromium's `--host-resolver-rules="MAP lan-host.test 127.0.0.1"`; the web tests use `https://testserver`.
- `run_mac.command` and `run_windows.bat` decide whether to download the model by its whole name, as `model.local_model_ready` decides whether the app can use it, and never by the model family: `qwen2.5:3b` is not `qwen2.5:7b`, and the app waits for the model `FELIXA_LOCAL_MODEL` names, so a script that took the 3b for the 7b skipped the download and left both Run buttons disabled. The Mac script reads a name with no tag as `name:latest`, as the app does. The Windows script looks a name up as written, and `ollama list` shows `name:latest`, so it downloads a name with no tag on every start (a short check with the registry). `LocalStart` in `tests/test_app.py` holds the app, the Mac script (run for real, with `ollama`, `pip` and `python` replaced by small scripts) and the Windows script to one table of cases. cmd.exe cannot run in the tests, so for `run_windows.bat` the test reads the options of its `findstr` line (`/b`, `/l`, `/c:`) and applies them to the listing as findstr documents them: a change to that line has to be tried on Windows.
- Both launchers read `.env`, and not alike. `run_mac.command` sources it in bash, which ends a line at a comment. `run_windows.bat` reads it with `for /f "usebackq eol=# tokens=1,* delims=="`: a line that begins with `#` is skipped, and on any other line everything after the first `=` is the value, so a comment after a value would become part of it (a password of `hunter2   # set to require sign-in`, a host name no computer has, a limit that is not a number and falls back to its default without a word). `.env.example` therefore puts every comment on a line of its own and keeps a setting that has no value commented out. Do not make `config.py` strip a trailing `#...` instead: a password may contain a `#`. `LocalStart` applies the options of the `for /f` line to the file as cmd documents them (`windows_env`, as it does for `findstr`) and checks that `.env.example`, with every setting switched on, means the same to bash and to that line; a change to the `for /f` line has to be tried on Windows too.
- Nothing a person reads names an exception. The message of a task (`pipeline.run_full`), the `reason` of a Vibe Check run that gave no result and the note on an upload that could not be read (`UNREADABLE` in `app.py`) are plain sentences. The exception goes to the log (`log.exception`, or a warning that carries `type(e).__name__`), and the engine keeps its last one apart in the result's `detail`, which no page, PDF or CSV prints (the command line does). A task that gave some results but not all is `complete`, because there is a report to open, and its message opens with `pipeline.WITH_PROBLEMS` ("Finished with problems"): `workspace.html` shows that as a warning panel (`.job-problem`) with a short heading over the sentences, so a partial result never reads as a success. A task that gave none is `failed`, with the same panel and the heading "This task did not finish". The written guidance is a step of its own in `_behaviour`: when only it fails, the ratings are saved and the message says only that the guidance is missing, and guidance is never asked for on ratings whose metrics were not made. While a task is queued or running the progress text stays the `h2#job-message` that the page's script rewrites; once it has ended, a long message is a `p`, never a 28 px heading.
- A part of the report that has no results is said so, never left out: `report.gaps` returns a `(title, reason)` pair for each of the signal ratings (`NO_BEHAVIOUR`), the guidance when only it is missing (`NO_GUIDANCE`) and a Vibe Check with no run at all (`NO_VIBE`: the task was cancelled before it saved one, or could not save it), and the page (`_results.html`, so the workspace too), the cover of the PDF and the CSV all print that one list. It is `[]` while there is no report (`has_results` is false), so a new workspace or an all-failed run says nothing. The reasons say "not run, or did not finish" and never "failed": "Run Vibe Check only" leaves the same stored state as a rating that did not finish (no ratings, a Vibe Check), and nothing records which of the two it was. A Vibe Check run that gave no result is not in the list: `render_html` and `csv_rows` already print its own "Not run". A new part of the report needs an entry in `gaps` and a test in `PartialFailures` (`assert_missing`).
- Nothing from an upload goes into `instructions`, the model's system text. An upload reaches the model only as `input_text`, and a source name is upload text too.
- Text a person typed can be one long string with no place to break: a profile URL as a name, a handle, a number of 300 digits (`1e300` is a valid target). A box that cannot wrap it grows past its card and widens the whole page, which can push the buttons off the screen. `.page` in `static/style.css` sets `overflow-wrap: anywhere`, so every box inside it wraps such a string and a new box needs no rule of its own. It has to be `anywhere`: `break-word` leaves the smallest width of a box alone, and a grid or flex child still could not shrink. `.page table` and `.page .btn` switch it off again, because wrapping inside a table (which scrolls in its own `.table-wrap`) squeezes the columns until "Positive" is split, and a button label is never typed by a person; a new kind of table or button needs the same opt-out. `Layout` in `tests/test_app.py` holds the stylesheet to this, but a test cannot draw a page: after a layout change, open a workspace and a report whose name is a 100-character URL at 1280, 768 and 390 px and check that the page does not scroll sideways.
- A chart is drawn once in a fixed scene (`charts.W`, 720 units wide, and `charts.NARROW_W`, 360, for a phone) and the browser scales it to its box, so a label is as large on the screen as its size in the scene times box width / scene width: 12 units in a 543 px box is 9 px. Work out the narrowest box a chart gets before choosing its text size. The score meter has the narrowest one, the hero's second column (543 px from a 1,001 px window), which is why `.vc-hero` is one column up to 1,000 px (at 761 px the column was 303 px and the 0, 5 and 10 came out at 5 px) and why the meter's labels are 16 units; `Charts.test_the_meter_scale_is_large_enough_for_the_narrowest_box_the_hero_gives_it` holds them to 12 px. A test cannot draw a page: after a change to a chart or to the hero, measure it in Chromium, for every visible `svg.vc-svg` as `font-size * svg.getBoundingClientRect().width / svg.viewBox.baseVal.width`, at 360, 768 and 1001 px. The other charts keep labels of 12 to 13 units, a known limit (see `VIBE_CHECK.md`): the table under each chart carries every value.
- A closed `<details>` prints as its summary line alone, so a printed report (Open report, then Print or Save as PDF) would lose whatever is folded away: the table under each chart, the flagged messages past the tenth, the forecast factors and the note on what limits the numbers. `vibe_check.render.JS` opens every closed `details` inside a `.vc` on `beforeprint`, and when the print media query starts to match (all that some browsers send), and shuts exactly those again on `afterprint`, so a fold the reader had opened stays open; the list of what it opened only grows while printing, because a second signal for the same print finds nothing left to open and must not make it forget the first one's. A `::details-content` rule in `render.CSS` shows a closed fold in print when no script runs. A new fold has to sit inside a `.vc` (the test of the report page checks it) or it prints closed; the delete confirmation of the workspace is outside one on purpose. A test can only read the script: after a change, print a report in Chromium (`page.pdf()` on `/analysis/N/report`) and search the text with `pdftotext` for a table header (`EXPRESSION STRENGTH`), the last flagged message and `prompt for review` (join the lines first: the phrase wraps), and check that no fold is left open afterwards.
- A printed report has three things that a test of the page cannot see, so a test reads the stylesheets and a person prints. (1) A browser leaves out background colours unless the reader asks for them, so light text on a dark box prints as pale text on white: `.confidence` (white on `#252d38`) printed at 2.3:1. `@media print` at the end of `static/style.css` gives it dark text, a white background and a border, which reads the same with the setting on or off; any new box with light text on a dark fill needs the same. (2) The print block of `templates/report.html` hides the brand header, the buttons and the skip link by class, with `!important`: a rule on the tag (`header{display:none}`) is less specific than `.topbar{display:flex}`, lost, and the header printed. (3) A heading stays with what it introduces. Every chart of the Vibe Check, with its heading and the note under it, is one `div.vc-keep` (`_keep` in `vibe_check/render.py`, `break-inside: avoid`), because Chromium does not hold a chain of `break-after: avoid` from heading to note to chart: depending on where the page ends, it breaks the chain between the note and the chart, or moves everything before the heading instead. A table twin stays outside the block, since it can be long. Headings that introduce a list or a table, and the host's own sections, rely on `break-after: avoid` and on tiles, cards and list items that are not cut in two. `Print` in `tests/test_app.py` reads the real stylesheets with a small cascade (`Cascade`: tags, classes, descendant and child selectors, `!important`, specificity, order) and asks what the header, the confidence box and every heading, tile, card and chart of a full report get on paper; `Render` in `tests/test_vibe_check.py` checks that each chart sits in a `vc-keep` that opens with its heading. After a change to any of it, print the report in Chromium (`page.pdf({format: 'A4', printBackground: false, margin: {top: '10mm', ...}})`, which fires `beforeprint`, so the folds open) at several margins (0, 10 and 20 mm) and on Letter too, and check with `pdftotext -layout` that no page ends on a heading or a heading's note while its chart starts the next, and that the confidence box reads dark on white.
